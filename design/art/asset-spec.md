## 1. 源精灵图处理方案（切片）

### 1.1 实测事实（可靠，来自程序化分析）

| 项 | 值 |
|---|---|
| 文件 | `public/assets/sprites/niulai.png`（已就位，由主理人复制） |
| 尺寸 | 273 × 252 px |
| 格式 | PNG / RGBA（带透明通道） |
| 横向 | **无贯穿透明列**；帧横向紧密排列，列间距约 2–4px 缝隙 |
| 纵向 | **6 个内容块**，每块高 38px，块间 3–5px 透明间隔（gutter） |
| 列间距（pitch） | 21 px（273 ÷ 13 = 21，整除） |
| 行间距（pitch） | ≈ 42 px（38 内容 + ~4 间隔） |
| 每行动画帧数（实测） | 行0=13，行1=13，行2=13，行3=12，行4=10，行5=7 |
| 可见总帧数 | ≈ 69 帧 |

> ⚠️ **对最初「13列×12行、21×21」假设的修正**：逐行透明像素分析显示纵向只有 **6 个内容块**（间隔出现在 y≈42/85/127/168/210，而非每 21px 一处），因此这是 **6 行动画条 × 最多 13 列、单元约 21×42** 的布局，**不是 12 行 21×21**。请以本实测为准。
>
> 🔧 **帧数校正记录**：上表帧数已统一为「方式 B 列缝隙法」权威值（行0/1/2=13、行3=12、行4=10、行5=7，合计 69）。早期一次缝隙检测曾误计为 行2=11、行5=6（合计 61），后经过可视化 contact sheet 由用户逐行肉眼确认，现已废止；以 §1.3 / §1.4 同值为准。

### 1.2 推荐切片方式（⚠️ 已修订：优先方式 B）

> **关键修正**：源图角色**横向几乎贴边、列间仅 2–5px 缝隙**，且各行帧宽/间距**并不均匀**（尤其行5「win」帧宽且间距大，约 25–38px pitch）。因此「固定 21×42 网格」会**误切**——按 `Rectangle(21*col,…)` 取帧会把一帧横跨多格、或把缝隙算进帧，尤其行5 完全对不齐。**请勿用固定 21 宽网格做精确切片。**

**方式 B（推荐，逐行按列缝隙检测边界）← 工程采用此方式**

- 对每行（取该行动画条 y 范围）扫描**全透明列（整列 alpha=0）**作为帧分隔；相邻非透明列段即一帧。
- 逐行得到真实帧边界 `[x0,x1]` 与帧数，切片 `frame = Rectangle(x0, y0, x1-x0+1, 行高)`。
- 渲染关闭 `imageSmoothingEnabled`（最近邻）。
- 各行动画条 y 范围（已实测，gutter 已剥除）：行0=3–40、行1=45–82、行2=88–125、行3=129–166、行4=171–208、行5=213–250（行高均 38，含于 42 单元内）。

**方式 A（备选，仅作粗略占位/快速预览，不可用于最终精确切片）**

- 仅当接受「帧略错位、行5 不可用」时，可用 `Rectangle(21*col, 42*row, 21, 42)` 做临时预览；正式切片必须回到方式 B。

### 1.3 帧尺寸 / 帧数 / 每行动画含义（已确认·用户肉眼标定）

> ✅ **已确认（用户逐行肉眼标定）**：下表每行的动作段划分取代原先「整行=单动画」的推断。每行含多个动作段，游戏动画按行内帧区间（0-indexed 闭区间）切片，而非整行。各行帧总数以 §1.1 列缝隙法实测为准；代码对区间做 clamp，越界自动回退该行首帧，不会因 ±1 计数误差崩溃。

| 行 | 0-indexed 动作段（用户标定） | 说明 |
|---|---|---|
| 0 | walk 0–5；正面待机/呼吸 6–12 | 正面图（左右对称），待机段用于 idle |
| 1 | 背面 walk 0–5；背面待机 6–12 | 背面图——旧代码误把 run 映射到此行，导致「背影」bug（已修正） |
| 2 | 侧面 walk 0–5；站立 6；欢呼/举手 7–11；站立 12 | 庆祝段用于 win |
| 3 | 攻击 0；嘲讽/叉腰 1–5；蹲 6；思考/挠头 7–9；倒地 10；起身 11 | 本游戏暂不用 |
| 4 | 侧面奔跑 0–5；施法/指引 6–9 | 侧视朝左；run/jump/fall/dash 取 0–5，引擎内水平翻转朝右 |
| 5 | 捂脸痛 0；滑铲/跌倒 1；踉跄/醉酒步 2–5；站立 6 | hurt 取 0–5；slide 取单帧 1 |

### 1.4 工程实现切图参数（已确认·用户肉眼标定）

> ✅ 切片仍用方式 B（§1.2）逐行检测，不用固定 21 宽网格。下方「动画 → 行内帧区间」为**已确认**映射（取代 §1.3 旧表的整行推断）。

- **逐行切片（方式 B）**：对每行 y 范围（行0=3–40 / 行1=45–82 / 行2=88–125 / 行3=129–166 / 行4=171–208 / 行5=213–250），检测全透明列缝隙得到每帧 `[x0,x1]`，切片 `Rectangle(x0, y0, w, 38)`（`w = x1-x0+1`）。
- **动画 → 行内帧区间（已确认，0-indexed 闭区间）**：

| 动画状态 | 来源行 | 行内帧区间 | 说明 |
|---|---|---|---|
| idle | Row 0 | [6–12] | 正面呼吸待机循环 |
| run | Row 4 | [0–5] | 侧面奔跑 |
| jump | Row 4 | [0–5] | 源表无专用跳帧，空中复用 run 姿态 |
| fall | Row 4 | [0–5] | 同上，复用 run 姿态 |
| hurt | Row 5 | [0–5] | 捂脸+滑铲+踉跄，受击/硬直序列 |
| win | Row 2 | [7–11] | 欢呼/举手庆祝 |
| slide | Row 5 | [1–1] | 滑铲单帧，滑铲机制未实装前为占位 |
| dash | Row 4 | [0–5] | 占位，复用 run |

- **水平翻转**：Row 2/4/5 为侧视图（朝左绘制），而牛来向右自动跑，故引擎在创建 AnimatedSprite 后执行 `scale.set(-SPRITE_SCALE, SPRITE_SCALE)` 全局水平翻转朝右；锚点仍为 (0.5,1)，绕中心原地翻转不位移；正面待机（Row 0）左右对称，翻转无视觉影响。命中盒/金币判定基于 player.x/y 与常量，不受翻转影响。
- **行内帧数说明**：各行动画条帧总数以 §1.1 列缝隙法实测为准（行0/1/2=13、行3=12、行4=10、 行5=7）。代码先取该行全部检测帧，再按上表区间切片；区间越界自动 clamp，空切片回退该行首帧，不会因计数 ±1 误差导致 AnimatedSprite 空纹理报错。
- **slide（滑铲）/ dash（冲刺）**：源图无独立帧，**临时复用 Row 4 奔跑帧占位**——slide 加水平压扁（squash），dash 加代码残影/速度线；是否补独立帧由 GDD 玩法定稿后决定。
- **变更流程**：若后续需调整映射，仅改上表 `row` / `from` / `to`；各行 y 范围基准（§1.2）不动。

## 2. 角色像素归并（源图→干净像素）⚠️ 已取消

> 🚫 **本节已取消**：用户决策直接使用现状精灵图，本节所述「归并 3 档明度 / 去抗锯齿 / 导出 niulai_clean.png」**不再执行**。保留下方分析仅作风格参考，现状 `niulai.png` 原样使用。

源图实测主色为金色 `#E8B30F` 系，但同一金色存在 **10+ 个近似抗锯齿色**（如 `#E8B30F`/`#E9B410`/`#F4C63F`/`#EBB610`…），描边为 `#2F1300`。为符合 art-bible §3 的「3 档明度」要求：

1. 将全部金色近似色归并到 3 档：**亮 `#F4C63F` / 中 `#E8B30F` / 暗 `#C98A0A`**。
2. 描边统一为 `#2F1300`（1px）。
3. 导出为 **索引色（indexed, ≤16 色）PNG**，去除抗锯齿。
4. 输出两份：原始 `niulai.png`（占位/调试）与重制 `niulai_clean.png`（正式）。
